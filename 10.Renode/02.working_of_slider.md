# Renode Hardware Wiring: Virtual GPIO Slider & Buttons

---

## 🧠 Core Concepts

* **The Virtual Breadboard / Schematic Concept:**
  In Renode, a `.repl` platform description is not just an abstract configuration file; it is a literal software schematic diagram. Just like placing a mechanical component on a physical PCB, placing a virtual component in Renode does nothing until you draw the signal trace (wire) connecting it to a microcontroller pin.

* **Deconstructing `.repl` Hardware Wiring Syntax:**
  ```repl
  slider0: Miscellaneous.Button @ gpioPortB 0 { IRQ -> gpioPortB@0 }
  ───┬───  ──────────┬─────────   ────┬──── ─┬ ─────────────┬─────────
     │               │                │      │              │
     │               │                │      │              └─ [4] Signal Wire (Copper Trace)
     │               │                │      └─ [3b] Pin / Index parameter (0)
     │               │                └─ [3a] Parent Peripheral on System Bus
     │               └─ [2] Renode C# Hardware Model Type
     └─ [1] Virtual Device Instance Name
  ```
  1. **`slider0:`** The unique identifier for this component. This is the handle you use inside Renode `.resc` scripts or CLI commands (e.g., `sysbus.slider0 Press`).
  2. **`Miscellaneous.Button`:** The built-in Renode C# hardware model simulating a mechanical tactile switch contact. It maintains electrical state: released = `LOW` (0V), pressed = `HIGH` (3.3V).
  3. **`@ gpioPortB 0`:** Attaches this component to the STM32 Port B peripheral controller at index/sub-address `0`.
  4. **`{ IRQ -> gpioPortB@0 }`:** The physical copper trace. In Renode, all digital GPIO signal lines are modeled as `IRQ` endpoints:
     * `IRQ`: Outgoing signal line from the button.
     * `->`: Directed connection ("wire this output to this input").
     * `gpioPortB@0`: Target connection point (Pin 0 of STM32 GPIOB, i.e., `PB0`).

* **What Happens in Silicon & Registers (The Low-Level View):**
  When you execute `sysbus.slider0 Press`:
  1. The `Miscellaneous.Button` model drives its `IRQ` line `HIGH` (3.3V).
  2. That signal travels along the virtual wire into `gpioPortB` Pin 0.
  3. Renode's STM32 GPIO peripheral controller flips bit 0 of the **`GPIOB->IDR` (Input Data Register)** from `0` to `1`.
  4. Inside firmware running on the virtual Cortex-M4 CPU:
     ```c
     int val = gpio_pin_get(gpiob_dev, 0); // Reads bit 0 of GPIOB->IDR
     ```
     Zephyr RTOS reads `val == 1`, identifies the contact as active, and transitions the mixer motor state. The firmware has zero knowledge that it is running inside an emulator.

* **The "Virtual Hand" Test Harness Pattern:**
  Production firmware should never contain hardcoded test sequences (e.g., `0 -> 2 -> 6 -> 0`). Firmware should strictly be reactive: reading GPIO pins and driving actuators. 
  Renode acts as the physical human hand in your test harness:
  * In `.repl`: We define 11 button contacts (`slider0` to `slider10`) wired to `PB0` through `PB10`.
  * In `.resc`: We simulate moving the lever across contacts using `Press` and `Release`.

## 🛠️ Playbook & Commands

**1. Interactively Control Slider Contacts in Renode Console:**
```text
# Slide to Speed 2 (Engage PB2 contact)
sysbus.slider2 Press
emulation RunFor "1.0"

# Slide to Speed 6 (Release PB2, Engage PB6)
sysbus.slider2 Release
sysbus.slider6 Press
emulation RunFor "1.5"

# Return to Stop / Idle (Release PB6)
sysbus.slider6 Release
emulation RunFor "1.0"
```

**2. Inspect GPIO Pin State from Renode Monitor:**
```text
# Check if PB2 is currently HIGH (True) or LOW (False)
sysbus.gpioPortB.pin2 State

# Watch for pin transitions live in the console
sysbus.gpioPortA.UserLED WatchState
```
