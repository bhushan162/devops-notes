###  Renode Mental Model & Architecture

 1. Why Renode Exists (The Whirlpool Overheating Problem)

  Imagine this real-world scenario at Whirlpool:
  > You write firmware for a washing machine motor controller.
  > If the motor temperature exceeds 85°C, your firmware must instantly trigger a safety shutdown, cut power to the drum, and flash a red error LED.

  How do you test this traditionally?
   1. Option A (Dangerous & Slow): You take a heat gun at your desk, blast hot air onto the real STM32 circuit board and sensor, and hope you don't melt the plastic or burn your hands.
   2. Option B (QEMU): You try running it in QEMU, but QEMU deadlocks because there is no I2C sensor model to reply with temperature data.
   3. Option C (Renode): You launch Renode, load the STM32 board, and type a single command:

   1    i2c1.temperature_sensor SetTemperature 88
     Renode instantly feeds 88°C over the virtual I2C bus into your firmware's register! You watch your firmware catch the over-temperature event and shut down cleanly.


2. The "Lego Block" Philosophy
    Renode is built on a modular "Lego block" architecture:
    * Antmicro has already built software models for hundreds of microcontrollers (STM32, NXP, Nordic, RISC-V) and sensors (temperature, accelerometers, EEPROMs, displays).
    * You configure your board using simple, human-readable text files—no C programming required!


  3. The Two Core File Types: .repl and .resc

  Just like Zephyr has prj.conf and .dts, Renode divides everything into two files:

    1 ┌────────────────────────────────────────────────────────┐
    2 │                THE TWO PILLARS OF RENODE               │
    3 ├───────────────────────────┬────────────────────────────┤
    4 │ 1. Platform (`.repl`)     │ 2. Script (`.resc`)        │
    5 ├───────────────────────────┼────────────────────────────┤
    6 │ • Describes HARDWARE      │ • Controls ACTIONS         │
    7 │ • "The Virtual Schematic" │ • "The Test Playbook"      │
    8 │ • Which chips exist and   │ • Load ELF, start CPU,     │
    9 │    how they are wired.    │    feed sensor data, stop. │
   10 └───────────────────────────┴────────────────────────────┘

  Pillar 1: .repl (Renode Platform Description)
  This is literally a software schematic diagram of your board.
  For example, to attach an I2C temperature sensor to an STM32:

   1 // Use the built-in STM32F4 chip definition
   2 using "platforms/cpus/stm32f4.repl"
   3
   4 // Snap a TI TMP102 temperature sensor onto the I2C1 bus at address 0x48
   5 sensor: Sensors.TMP102 @ i2c1 0x48
   6
   7 // Snap an LED onto GPIO Port A, Pin 5
   8 userLed: Miscellaneous.LED @ gpioPortA 5

  Pillar 2: .resc (Renode Script)
  This is an automation script. It tells Renode what to do step-by-step:

    1 # 1. Create a virtual machine named 'smart-appliance'
    2 mach create "smart-appliance"
    3
    4 # 2. Load the hardware blueprint
    5 machine LoadPlatformDescription @board.repl
    6
    7 # 3. Load the compiled firmware ELF binary
    8 sysbus LoadELF @build_stm32/zephyr/zephyr.elf
    9
   10 # 4. Open the UART serial port
   11 showAnalyzer sysbus.usart2
   12
   13 # 5. Power on the virtual microcontroller!
   14 start

  4. QEMU vs. Renode: The Interview Comparison

  When an interviewer asks you:
  > "Why did you use both QEMU and Renode in your CI/CD pipeline? Aren't they both just emulators?"

  ┌──────────────────┬──────────────────────────────────┬────────────────────────────────────────────────────┐
  │ Metric           │ QEMU (qemu-system-arm)           │ Renode (Antmicro)                                  │
  ├──────────────────┼──────────────────────────────────┼────────────────────────────────────────────────────┤
  │ Primary Job      │ Ultra-fast CPU smoke testing     │ Full-system & peripheral integration               │
  │ Boot Speed       │ Sub-second (~0.5s)               │ Slower (~3–5s due to .NET runtime)                 │
  │ Hardware Scope   │ Single MCU core, basic UART      │ Multi-node (can connect 2 MCUs via CAN/BLE)        │
  │ Sensors & Wiring │ ❌ Deadlocks on missing ACKs     │ ✅ Built-in models (I2C, SPI, Buttons, LEDs)       │
  │ Fault Injection  │ ❌ Not possible                  │ ✅ Inject temperature, button clicks, packet drops │
  │ Role in Pipeline │ Stage 4: Fast gatekeeper for PRs │ Stage 5: Hardware-accurate integration tests       │
  └──────────────────┴──────────────────────────────────┴────────────────────────────────────────────────────┘

* ** Installing Renode in Docker ** 
    * 
    ```
    docker run -it --rm \
    -v $(pwd):/workspace \
    -w /workspace \
    antmicro/renode renode --disable-ui -e "s @stm32_startup.resc"

    ```

    * --disable-ui` flag so Renode executes without requiring a graphical display server
    * ### **Executing Automated Tests with** **renode-test**

        For continuous integration, invoke the batch runner `renode-test` to execute **Robot Framework** test suites non-interactively inside the container[4]:

        ```
        docker run --rm \
        -v $(pwd):/workspace \
        -w /workspace \
        antmicro/renode renode-test tests/my_firmware_tests.robot

        ```

        * **Outputs:** Automatically writes HTML test reports (`report.html`), execution logs, and failure **state snapshots** to your mounted workspace directory[2].
