## Why Helm Exists (The Problem of "YAML Sprawl")
- Now imagine we need to deploy VaultAstra to 3 environments:
- dev (1 replica, small CPU/memory, tag v1.0.0-dev, domain dev.vaultastra.local)
- Staging (2 replicas, medium resources, tag v1.0.0-rc1, domain staging.vaultastra.local)
- prod (5 replicas, high resources, tag v1.0.0, domain vaultastra.com)
- Without Helm, you have to duplicate every single Deployment, Service, and Ingress file 3 times. If you change a port number or probe path later, you must manually edit dozens of YAML files. 


## The 3 Core Helm Concepts
1. Helm Chart: The packaged bundle of YAML templates and default configuration files (think of it as an npm package or a Debian .deb file, but for Kubernetes).
2. values.yaml: The variables file. This is where you store your environment-specific settings (replica count, image tags, CPU limits).
3. Helm Release: A running instance of a chart inside the cluster. You can install the same vaultastra-backend chart three times to create three independent releases: vast-backend-dev, vast-backend-staging, and vast-backend-prod.

## Anatomy of a Helm Chart
```
vast-backend/
├── Chart.yaml          # Metadata: Chart name, version (1.0.0), appVersion
├── values.yaml         # Default configuration values (variables)
├── templates/          # Jinja2 / Go-template YAML files
│   ├── deployment.yaml # Dynamic deployment template
│   ├── service.yaml    # Dynamic service template
│   ├── ingress.yaml    # Dynamic ingress template
│   └── _helpers.tpl    # Reusable template snippets and label generators
└── .helmignore         # Files to ignore when packaging
```


## How Templating Works: Static YAML ➔ Helm Template

### 1.The Variable File (values.yaml)

```yaml
replicaCount: 2

image:
  repository: vaultastra/ledger-api
  tag: "1.0.0"
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80
  targetPort: 8080

resources:
  limits:
    cpu: 250m
    memory: 256Mi

```

### 2. The Dynamic Template (templates/deployment.yaml)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-api
  labels:
    app.kubernetes.io/name: {{ .Chart.Name }}
    app.kubernetes.io/instance: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app.kubernetes.io/name: {{ .Chart.Name }}
      app.kubernetes.io/instance: {{ .Release.Name }}
  template:
    metadata:
      labels:
        app.kubernetes.io/name: {{ .Chart.Name }}
        app.kubernetes.io/instance: {{ .Release.Name }}
    spec:
      containers:
      - name: {{ .Chart.Name }}
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
        imagePullPolicy: {{ .Values.image.pullPolicy }}
        ports:
        - name: http
          containerPort: {{ .Values.service.targetPort }}
        resources:
          {{- toYaml .Values.resources | nindent 10 }}
```


Action,Command,What it does
Lint / Validate,helm lint ./vast-backend,Checks your chart for syntax errors.
Dry-Run (Render),helm template my-release ./vast-backend,Previews the rendered YAML without applying it to the cluster.
Install / Deploy,helm install vast-dev ./vast-backend -n vast-dev,Deploys the chart to the cluster for the first time.
Upgrade / Update,helm upgrade vast-dev ./vast-backend -f values-dev.yaml -n vast-dev,Updates an existing release with new values or template changes.
Atomic Rollback,helm rollback vast-dev 1 -n vast-dev,Instantly reverts the release back to revision 1.
List Releases,helm list -n vast-dev,Shows all active Helm releases in the namespace.
