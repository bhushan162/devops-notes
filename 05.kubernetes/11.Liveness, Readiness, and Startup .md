# Liveness, Readiness, and Startup Probes
- Kubernetes uses Probes to monitor the health of containers running inside Pods.

## In Kubernetes, there are three primary types of probes:

1. Liveness Probe — Checks if the container is still running.
2. Readiness Probe — Checks if the container is ready to accept traffic.
3. Startup Probe — Checks if the container has successfully started.

```yaml
spec:
  containers:
  - name: ledger-api
    image: vaultastra/ledger-api:v1.0
    ports:
    - name: http-api
      containerPort: 8080

    # 1. STARTUP: Gives the app up to 30 * 2s = 60s to boot up
    startupProbe:
      httpGet:
        path: /health/startup
        port: http-api
      periodSeconds: 2
      failureThreshold: 30

    # 2. READINESS: Checks every 5s if app is ready to take customer transactions
    readinessProbe:
      httpGet:
        path: /health/ready
        port: http-api
      periodSeconds: 5
      failureThreshold: 3

    # 3. LIVENESS: Pings every 10s to detect frozen threads or deadlocks
    livenessProbe:
      httpGet:
        path: /health/live
        port: http-api
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3

```

#### scinario 1 
``scinario`` : The "502 Bad Gateway" During Deployments , 
``Component Affected``: Frontend & Backend Deployments
``steps`` : Developer runs: kubectl set image deployment/backend api:v2 get 502 Bad Gateway
``The Real-World Problem:``:When you release v2 of your Backend API, the container process starts in 1 second, but your code takes 15 seconds to parse environment variables, warm its cache, and establish its database connection pool. Without a readiness probe, Kubernetes immediately routes live users from the Frontend to this half-awake Backend pod. Your users get 502 Bad Gateway errors for 15 seconds on every deployment.
``The Solution:`` The readinessProbe blocks traffic from entering the Pod until your backend explicitly responds with HTTP 200 on /health/ready. Kubernetes keeps routing traffic to the old v1 pods until v2 is truly ready, achieving zero-downtime deployments.
