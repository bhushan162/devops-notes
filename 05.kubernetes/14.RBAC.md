# RBAC
- RBAC (Role-Based Access Control) is Kubernetes' security framework that regulates who can perform what actions on which resources.
- By default, Kubernetes follows the Principle of Least Privilege (PoLP): every identity starts with zero permissions until explicitly granted.

## The 3 Core Pillars of RBAC
```
 ┌──────────────────────┐         ┌──────────────────────┐         ┌──────────────────────┐
 │     1. SUBJECT       │         │      3. BINDING      │         │       2. ROLE        │
 │       (WHO?)         │ ──────► │       (THE GLUE)     │ ──────► │       (WHAT?)        │
 │                      │         │                      │         │                      │
 │ • User (Human)       │         │ • RoleBinding        │         │ • API Groups         │
 │ • Group (Team)       │         │ • ClusterRoleBinding │         │ • Resources (Pods)   │
 │ • ServiceAccount(App)│         │                      │         │ • Verbs (get, delete)│
 └──────────────────────┘         └──────────────────────┘         └──────────────────────┘
```
1. Subject (Who is asking?): A human developer (User), an engineering team (Group), or an automated CI/CD pipeline / Pod process (ServiceAccount).
2. Role / ClusterRole (What is allowed?): A list of explicit permissions defined as apiGroups + resources + verbs.
3. RoleBinding / ClusterRoleBinding (The Link): The permission badge that assigns a Role to a Subject.

## Namespace Scope vs. Cluster Scope

ScopePermission DefinitionAssignment ObjectWhat it can controlNamespace-ScopedRoleRoleBindingResources inside one room (e.g., Pods, Deployments, Secrets in vast-dev).Cluster-ScopedClusterRoleClusterRoleBindingNon-namespaced items (Nodes, PVs, Namespaces) or all namespaces across the cluster.

Architect Pattern: You can also bind a global ClusterRole (like the built-in view or edit role) using a namespaced RoleBinding. This grants the user read access only inside that specific namespace without needing to write duplicate Roles everywhere!


## Real-World Example:

### 1. Create a dedicated ServiceAccount
```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: vast-cicd-deployer
  namespace: vast-dev
```

### 2. Create the deployment Role
``` yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: vast-cicd-role
  namespace: vast-dev
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "update", "patch"]
- apiGroups: [""]
  resources: ["pods", "services"]
  verbs: ["get", "list"]

```

### 3.Create the RoleBinding
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: vast-cicd-binding
  namespace: vast-dev
subjects:
- kind: ServiceAccount
  name: vast-cicd-deployer
  namespace: vast-dev
roleRef:
  kind: Role
  name: vast-cicd-role
  apiGroup: rbac.authorization.k8s.io
```

### 4. test 

```bash
    # Check if the CI/CD service account can update deployments in vast-dev:
    kubectl auth can-i update deployments \
    --as=system:serviceaccount:vast-dev:vast-cicd-deployer \
    -n vast-dev
    # ➜ Output: yes

    # Check if it can delete secrets in vast-dev:
    kubectl auth can-i delete secrets \
    --as=system:serviceaccount:vast-dev:vast-cicd-deployer \
    -n vast-dev
    # ➜ Output: no (Blocked by RBAC!)
```
